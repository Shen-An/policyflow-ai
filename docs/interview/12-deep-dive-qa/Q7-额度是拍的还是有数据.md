# Q7 · 8 次这个数字怎么定的？是拍的，还是你观察过真实调用分布？

> 原话：「8 次这个数字是怎么定下来的？是拍的，还是你观察过真实问题的调用分布？」
> 紧接着：「你观察过实际跑下来，一次回答平均调几次工具？有没有出现过撞到 8 次上限的 case？」

**他在考什么**：**你会不会编数字。** 这是个陷阱题——他先问「是不是拍的」，给了你台阶；你要是硬说「观察过」，他立刻追平均值和 case，你就得现编。

---

## 🚨 2026-08-25 实测：这题我答砸了

| 我当时说的 | 实际情况 |
|---|---|
| 「我觉得 8 次足够用」 | **等于承认是拍的**，但没说设计意图，白丢分 |
| 「**撞到过上限**」 | ❌ 编的。**真实数据是 0 次撞上限**（见下） |
| 「**一般 5 到 6 次就能完成**」 | ❌ 编的。**真实平均 1.03 次**，编大了 5 倍 |
| 「撞上限的都是**无效工具调用**」 | ❌ 编的，后面被追「举个具体例子」，只能继续编——**而真实的例子是有的**（见下） |

**编一个数字，他会追三个问题**，每一个都得用新的编造去圆。这是本场最危险的地方——比答「不知道」扣分重得多。
更讽刺的是：**这些数字本来就能算出来，而且算出来的版本比我编的更好用。**

---

## ✅ 2026-08-26 补跑：现在有真数据了

复现命令（脚本在仓库里）：

```bash
python scripts/analyze_tool_calls.py policyflow.db
```

### 样本与口径（先说清楚，别让他追）

- 样本 = 本地开发库 `policyflow.db` 里 **63 条助手回答**，其中 **35 条**带 `diagnostics`（早期 28 条是旧 schema，没有 trace 字段，只能弃用）。
- 所以 **n = 35 轮**，是我自己开发调试期的流量，**不是线上真实用户分布**——这点必须主动说。
- 数据不是从 `tool_call_logs` 来的：那张表只记录**注册进 DB `tools` 表**的工具，而 Answer Agent 用的 `kb.search` / `skill.run` 没注册在那儿，所以表里 11 行全是手工/demo 调用，**AnswerAgent 行数 = 0**。真正的 trace 落在 `messages.meta_json → diagnostics.tools`。

### 结果

| 指标 | 值 |
|---|---|
| 每轮工具调用次数分布 | 0 次 ×21、1 ×1、2 ×7、3 ×4、4 ×1、5 ×1 |
| 平均 / 中位数 | **1.03 / 0** |
| p95 / 最大 | **4 / 5** |
| 一次工具都没调的轮次 | **21/35 = 60%** |
| 只看用到工具的 14 轮 | 平均 **2.57**，最大 **5** |
| **撞到 8 次上限的轮次** | **0** |
| 模型实际调过的工具 | `kb.search` 35 次、`skill.run` 1 次；另外 4 个（`draft.create`/`memory.read`/`memory.write`/`mcp.call`）**一次都没被自主调过** |

### 一句话结论

> **8 这个上限从来没被逼近过**，p95 是 4，一多半轮次连工具都不用。
> 也就是说这个数字确实是拍的，而且**拍得偏大**——但作为保险丝，偏大不算错，只是没优化过。

## 标准答法（约 60 秒，现在可以带数字了）

> **是拍的，我直说。** 它的定位是**保险丝，不是调优出来的最优值**——防的是工具循环失控把时间和钱烧光，不是卡正常请求。
>
> **不过我后来把分布算出来了**：开发期 35 轮里，平均 1.03 次，p95 是 4，最大 5，**一次都没撞到 8**；而且 60% 的轮次根本不调工具——因为主检索在 Answer 之前的 pipeline 里已经做完了，Answer 阶段的工具调用本来就是补充性质的。
>
> **要提醒一点，这是我自己开发调试的流量，n=35，不是线上分布**，所以我只把它当「上限拍得偏大」的证据，不当性能结论。

### 如果他追「那你会怎么改」

> p95 是 4，我会把上限从 8 降到 **5 或 6**——留一点余量，同时让失控更早暴露。
> 但我不会降到 4，因为样本太小，而且**跨文档比对类的问题天然要多查几次**，压太死会伤到正好该多查的那类问题。
> 反过来说，**如果**跑出来经常撞上限，那不该调大，**该去看是哪个工具在重复调**——撞上限通常说明有循环，调大只会烧更多钱。

### 如果他追「什么叫无效调用，举个例子」（这次有真例子了）

> **2026-08-20 有一轮，模型连发两次 `kb.search`，第二次直接失败了**，错误是「本轮 retrieval 调用次数已达上限」。
> 原因不是它调太多工具（那轮只用了 2/8 次工具额度），是**检索额度先花完了**：主检索已经占了 1 次，第一次补查占掉第 2 次，第三次就被保险丝拦下。
> 这正好说明**真正卡住模型的不是 8，是 2**——两个额度不是一回事。详见 [[Q4-Answer-Agent的决策空间]]。

## 顺手挖到的三件事（都能当加分料）

1. **LLM 调用额度真的被打满过。** 有两轮 `llm_calls = 8/8`（当时上限就是 8），一轮耗时 44.9 秒、一轮 36.3 秒。后来上限提到 **16**，就没再打满。所以「撞过上限」这句话如果说的是 **LLM 调用**，是真的；我当场说成工具，说错了对象。
2. **额度是改过的，不是一开始就这样。** 早期快照里 `max_tool_calls=6`、`max_total_seconds=90`，现在是 **8 / 180**。可以顺势说「这些数字我调过一轮，是照着观察到的耗时放宽的」。
3. **那些 3~5 次 `kb.search` 的轮次全在 2026-07**，早于 `2026-08-12` 那个提交（`a1ebe2f`，给 `kb.search` 加上 retrieval 额度）。也就是说**今天同样的问题会在第 1 次补查后就被截断**——分布是在更松的约束下测的，这点得说明，不然数字会被他质疑。

## 这题的通用心法

他问「是拍的还是测的」时：

1. **是拍的就说是拍的**，然后立刻补**设计意图**（这是保险丝 / 这是保守值 / 这是为了防什么），别停在「我觉得够用」。
2. **有数据就报数据，并且主动交代口径**（n 多少、什么流量、什么时期的代码）。自己说边界，比被他挖出来强得多。
3. **主动说拿到数据会怎么改**——证明这个数字对你不是摆设。
4. 没测过就说没测过 + 数据在哪 + 怎么测。「没做」和「不知道怎么做」是两个档次。

> 这次的教训很具体：**我编的「平均 5-6 次」，比真实的「平均 1.03、p95 4、从未撞顶」还难讲。**
> 真数据自带一个漂亮结论（上限拍偏大了，我知道该降到几）；编的数字只会把我推向更多编造。

---

## 别这么答

- ❌ 编平均值、编 case。他一定会追细节，你得用新的编造去圆。
- ❌ 「我觉得够用」然后没了——等于承认拍脑袋还不给理由。
- ❌ 报数字不报口径。n=35 的开发期数据说成「线上表现」，被追一句「多少样本」就崩。
- ❌ 把「LLM 调用打满」和「工具调用撞顶」混着说——前者真发生过，后者从没有。
