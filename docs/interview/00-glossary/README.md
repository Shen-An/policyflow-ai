## 先记这 8 个（面试官最爱问）

| 术语 | 面试时你可以这么讲 |
|---|---|
| **RAG** | 「回答前先去知识库查相关段落，照着资料答，不靠大模型凭记忆瞎编；查不到就拒答。」 |
| **rerank（重排序）** | 「检索先粗筛一批，rerank 再排一次队把最相关的往前挪。我默认用本地词法版，另有可选的真 NVIDIA 云端重排，但默认关着、失败不偷偷降级。」 |
| **Skill vs Tool** | 「Tool 是一个原子动作（存草稿、查库）还会记日志；Skill 是业务规程（把证据整理成流程清单），没证据就说『证据不足』，不硬编。」 |
| **MCP** | 「一个让 AI 连外部系统（邮箱/日历/飞书）的标准接口。我这儿协议是真的，但企业连接器是演示用的假数据，响应里明确标 `mock`。」 |
| **Hit@K / MRR** | 「两个衡量检索准不准的分数：Hit@5 看正确资料有没有进前 5 条，MRR 看它排得多靠前。我报指标一定写清用哪种检索、测了多少条。」 |
| **Turn Budget（回合预算）** | 「给每问一次设的上限——最多调几次模型、查几次、跑多少秒，防止失控或越跑越久。」 |
| **hard refuse（硬拒答）** | 「查不到可靠依据时，宁可说『无法回答』也不瞎编。」 |
| **mock** | 「假的 / 模拟的：演示用假数据顶替真实外部系统，而且老实标出来，不冒充真接。」 |

## 1. 检索 & RAG（系统怎么「找资料」）

**RAG（检索增强生成）** — 回答前先去资料库找相关段落，让 AI「看着资料答」，而不是凭记忆编。*例：你问「年假几天」，系统先翻到《年假管理办法》那段，再照着它回答。*

**知识库（KB, Knowledge Base）** — 存制度文档的库，可分 HR / 财务等；按权限不同的人能看不同的库。

**切块 / chunk** — 把长文档切成小段再存，方便按段落检索和引用。*例：一篇年假办法切成 5 小段。*

**embedding（向量 / 嵌入）** — 把文字变成一串数字，意思相近的数字也相近；这样能按「意思」找，而不只是按字面。

**向量检索 / 语义检索** — 按「意思相近」找资料（靠 embedding）。*例：你问「请假」，也能找到写「休假」的段落。*

**BM25（关键词检索）** — 老牌的按「关键词字面重合」找资料的算法，快、稳、好解释。

**LightRAG** — 一个开源 RAG 框架，我用它做其中一条检索路径（还能抽关键词、建关系）。

**Hybrid（混合检索）** — 同时用 LightRAG 和 BM25 两路一起找，再合并结果。*这是我系统的默认检索方式。*

**RRF（排名融合）** — 把两路检索的排名「公平合并」成一个总排名的算法。

**rerank（重排序）** — 见上。把粗筛结果再排一次，最相关的往前。

**cross-encoder** — 用模型「逐条精判」相关度的高级重排方式。我这儿是**可选**的真 NVIDIA 云服务，**默认关着**，用不了会直接报错、不静默降级。

**lexical fusion（词法融合）** — 我**默认**用的本地重排：比「词重合度」，不用模型、不花钱、可解释。

**证据 / evidence** — 这一轮检索到、用来支撑回答的那些资料段落。

**引用溯源 / citation（`[n]`）** — 回答里标 `[1][2]`，点开能看到出处段落，证明不是瞎编。

**降级 / fallback（兜底退路）** — 某条路走不通就退而求其次。*例：LightRAG 超时了，就只用 BM25 的结果，并打标签说明「降级过」。*

## 2. AI 编排 & Agent（系统怎么「干活」）

**Agent（智能体）** — 能自己决定「要不要调工具、调哪个」的 AI，不只是一问一答。

**tool-using RAG** — 我项目的准确定位：一个「会用工具的检索问答 AI」。

**multi-agent（多智能体）** — 多个 AI 角色互相聊天协作。▸**面试可以说**：我特意说明我**不是**这种玩具群聊，而是一条确定的流水线 + 一个会用工具的主 AI。

**AgentPipeline（编排流水线）** — 把「路由 → 检索 → 回答 → 检查 → 记忆」串起来的主流程；聊天和评估共用同一套，不重复写两份。

**Router（路由）** — 每轮先判断：这问题要不要查库？难不难？要不要用 Skill？

**tool loop / function calling（工具调用环）** — 主 AI 一边想一边调工具、拿到结果再想，直到能回答。

**Skill（技能）/ Tool（工具）** — 见上。Tool = 一个具体动作；Skill = 一套业务规程。

**stdio / http（MCP 的通道）** — MCP 连接外部的两种方式，一种走本地进程、一种走网络；我这儿是真能连的。

**CoT / ToT（思维链 / 思维树）** — 让 AI「分步骤想」（链）或「想几条方案再挑最好」（树）；我按问题难度决定用哪种。

**Verifier / Compliance（质量 / 合规检查）** — 回答生成后再过一道检查，决定：通过、打回重写、还是拒答。

## 3. 记忆 & 多轮对话（系统怎么「记住你」）

**四层记忆（L0–L3）** — L0 = 原始每句话；L1 = 最近几轮 + 滚动摘要；L2 = 从对话里抽出的「事件摘要」；L3 = 记住的「实体」（比如你在哪个部门）。

**STM / LTM（短期 / 长期记忆）** — 短期 = 最近几轮；长期 = 值得长期留的信息。

**滚动摘要（rolling summary）** — 对话太长时，把前面内容压成一段摘要，省空间又不丢主线。

**salience（重要度）** — 给每条记忆打的「重要分」，决定要不要长期留、回忆时排多前。

**TTL（过期时间）** — 给不重要的记忆设「保质期」，到期自动清掉。

**query rewrite（查询改写）** — 把「给我模板」这种省略句，结合上文补成完整问题再去检索。▸**面试可以说**：短跟进句我会先改写，避免检索丢主题。

**entity（实体）** — 对话里的人 / 部门 / 项目等关键对象，单独记下来。

**冷 / 热（hot / warm / cold）** — 只是「拼提示词时」把最近的放热区、摘要放温区、按需召回的放冷区；**不是**三个独立存储。

**记忆非权威** — ▸**重要边界**：记忆只用来理解上下文（指代、风格、你之前说过啥），**绝不能盖过这一轮查到的制度证据**。

## 4. 兜底 & 健壮性（系统怎么「不出乱子」）

**Turn Budget（回合预算）** — 见上。给「每问一次」设的硬上限：最多 16 次模型调用 / 2 次检索 / 8 次工具 / 180 秒（`backend/app/agents/turn_budget.py`，可在 settings 调）。

**检索质量门（quality gate）** — 检索结果太空 / 太跑题时，先自动重试一次原问题，还不行就拒答。跑题怎么判见下面「跑题门控」。

**hard refuse（硬拒答）** — 见上。没可靠依据就明确说无法回答。

**PASS / REVISE / REFUSE（发布门）** — 回答出门前的三种判定：通过 / 打回重写 / 拒绝发出。

**幂等 / idempotency** — 同一个操作**重复做也不会重复生效**。*例：「把请假状态设为已提交」做十次还是已提交（幂等）；「发一封邮件」做两次就真发出两封（不幂等）。*

**幂等键（idempotency key）** — 给「同一件业务操作」贴的一个唯一编号，随请求一起带上。收到请求的一方先看这个编号：**没见过就执行，见过就直接返回上次的结果、不再执行第二次**。*例：去柜台交单子，单子上印着流水号；你不确定上次交成没交成又交了一遍，柜员一看流水号已经办过，就把上次的回执给你，而不是再办一次。* 我的键 = `sha256(用户 + 会话 + 工具名 + 参数)`（`backend/app/tools/chat_tools.py`），所以「同一个人、同一轮对话、同一个工具、同一套参数」必然算出同一个键。▸**面试可以说**：带着同一个幂等键重发是安全的（最多生效一次），这是外部副作用能安全重试的前提。▸**边界**：端到端幂等**需要外部平台认这个键**（成熟 API 如 Stripe 有 `Idempotency-Key` 请求头）；我现在是拿它查自己的调用日志去重，能防「同一轮重复调用」和「超时后盲目重发」，平台侧幂等要接真连接器才成立。展开见 [11 Q12](../11-scenario-questions/README.md)。

**unknown（状态未知）** — ▸**这是整套兜底的灵魂**：外部调用超时，最麻烦的不是「失败」，而是**你不知道对方到底做了没有**。所以超时记 `unknown` 而**不是** `failed`——`failed` = 确定没做，可以安全重试；`unknown` = 可能已经做了，重试就可能发出第二封邮件。同键遇到 `unknown` 时直接拒绝执行（报 `SIDE_EFFECT_STATUS_UNKNOWN`），交人核对，不自动重发。

**超时 / timeout** — 某一步太久就掐断，别拖死整轮。

**副作用 / side effect** — 对外部世界产生的真实影响，比如真发了邮件、真建了日程——**发出去就收不回**。

**回滚 / rollback** — 数据库出错时把这次改动撤销；但**撤不回**已经发出的邮件（那属于副作用）。

**Saga / 熔断（circuit breaker）/ 补偿** — 都是「生产级分布式系统」里更复杂的容错手段（Saga = 多步里某步失败就逐步倒着撤销；熔断 = 某个服务老坏就先暂停调用它；补偿 = 做个反向操作抵消影响）。▸**面试可以说**：这些我**明确没做**，我的兜底是单体应用里的基础版，靠确定性信号做判断。

## 5. 评估（怎么证明「效果好不好」）

**Hit@1 / Hit@5 / Hit@10** — 正确资料有没有出现在检索结果的前 1 / 前 5 / 前 10 条里。

**MRR** — 正确资料排得多靠前的平均分（排第 1 得 1 分、第 2 得 0.5 分…越靠前越高）。

**Recall@K** — 该找到的资料，前 K 条里找回了多大比例。

**HitAll@K** — 一题有多篇正确资料时，前 K 条是不是「全都」命中（比只命中一篇更严格）。

**金标 / gold** — 人工标好的「标准答案 / 正确资料」，用来给系统打分。

**干扰文档 / distractor** — 故意混进去的无关文档，让测试更难、更接近真实（避免库里就一篇、随便都 100%）。

**CRUD（数据集）** — 我用来量化检索的公开中文 QA 数据集，取它的 `questanswer` 部分当金标。▸这是我**量化主指标的权威来源**。

**RAGAS** — 一个自动评估「回答质量」的工具（可选；没装依赖就用替代指标并标注来源）。

**sanity vs benchmark** — sanity = 粗略自检「能不能跑对」；benchmark = 严格权威跑分。▸**面试可以说**：我自建的企业政策集是 sanity（小库 / 合成 / 无干扰），量化主张仍以 CRUD 为准。

**N（样本量）** — 这次测了多少条。▸**报指标必须同时说 N**，不然数字没意义。

**负样本 / negative（该拒答的题）** — 故意挑「库里根本答不了」的问题当考题，看系统会不会闭嘴。*例：库里只有 12 篇制度，没有婚假规定，那「婚假几天」的正确答案就是「查不到」。* ▸**为什么重要**：只测「答得准不准」量不出「该闭嘴时闭不闭嘴」，而企业助手答错制度比答不出更贵。▸**记法要点**：负样本**没有金标，所以不进 Hit@K / MRR**（进去要么白送 0 分把指标做低，要么白送满分），它们单独算「拦住率」；看板上 `N=` 只数正样本，负样本写 `neg=`。

**off_topic vs near_miss（负样本的两类）** — `off_topic` = 完全不沾企业语境（「明天北京天气」「快排怎么写」），是底线题，拦不住说明门控坏了；`near_miss`（近似题）= 一样的企业话术、一样的问法，**但库里没这个主题**（「婚假几天」「期权行权价」）。▸**面试可以说**：near_miss 是真难点——问婚假时库里没有婚假制度，但「假」「员工」「申请」这些词到处都有，光数词重叠很容易放过去。

**跑题门控（off-topic gate）** — 检索确实返回了片段、但片段跟问题没关系时，把证据丢掉按「查不到」拒答，而不是拿不相关的条款硬答。▸**我怎么做的**：有真 cross-encoder 分数时按分数判（低于阈值算跑题），没有就退回中文二元词覆盖率。▸**边界**：默认聊天不开重排 → 拿不到 cross-encoder 分 → 实际走的是词面兜底；阈值目前是保守值，还没标定完。

**误拦 / 拦截率（false block / block rate）** — 一道门必须同时报两个数才诚实：**误拦率** = 本该答的题被拦掉的比例（代价），**拦截率** = 该拒答的题被拦住的比例（收益）。▸只报一个数是耍花招——门槛调到无穷高，拦截率 100%，但什么都答不了了。

**A/B** — 同样条件下对比两种设置（比如两种 rerank）看谁好。

## 6. 后端 & 工程名词

**FastAPI** — 我用的 Python 后端框架（写接口用的）。

**SQLModel / SQLAlchemy / ORM** — ORM = 用写代码的方式操作数据库，不用手写 SQL；SQLModel、SQLAlchemy 是具体工具。

**SQLite** — 一个轻量、单文件的数据库，适合中小项目和演示。▸边界：不适合超大规模。

**WAL** — SQLite 的一种写入模式，让读和写不容易互相卡。

**SSE（流式输出）** — 让回答像打字机一样一段段实时冒出来，而不是等全部生成完才显示。

**JWT** — 登录后发给你的一张「令牌」，之后每次请求带着它证明你是谁。

**RBAC / ACL（权限）** — RBAC = 按角色给权限（员工 / 管理员）；ACL = 具体到「哪个库谁能看」。

**N+1（查询效率问题）** — 一种常见性能坑：本可一次查完，却在循环里查了很多次；我修过几处。

**BackgroundTasks（后台任务）** — 把「建索引」这类慢活丢后台跑，不卡住页面按钮。

**HITL（human-in-the-loop,人在环）** — 关键步骤停下来让人拍板。*例:ToT 给 2–3 个方案,让用户选一个再继续,不是全自动跑到底。*

**stale gold（过期金标）** — 评测用例的「标准答案」指向的文档已经被删或为空,这种用例跑出来的分数不准,要一键清掉。

**彩排（rehearsal）** — 面试前按演示脚本完整跑一遍,确认不翻车(项目里有 `scripts/rehearse_interview_checklist.py`)。

**Fake LLM / 注入适配器** — 测试时不调真大模型(省钱、稳定、可复现),塞个「你问啥它按预设回啥」的假货;靠依赖注入把假组件塞进系统。

**孤儿文件** — 文档被删了,但磁盘上的索引/切块文件还留着没人认领,删库时要一并清掉。
