# Feature Specification: 企业级智能体重构

**Feature Branch**: `master`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "重构 PolicyFlow AI，使其可支撑大规模企业用户并以压测证明容量，全面改善粗糙页面，统一智能体编排并建立真实文件沙箱，让获授权用户可编辑和提交报销等企业材料；沿用项目既定技术边界并严格遵守项目宪法。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 安全编辑并提交企业材料 (Priority: P1)

企业员工在获得角色权限后，可以选择或上传与业务任务相关的材料，让智能助手根据企业政策证据生成或修改工作副本，查看差异，并在明确确认后提交；例如根据报销政策整理报销材料。正式政策原件始终不可被智能助手直接改写。

**Why this priority**: 这是本次重构新增的核心业务价值，也是文件安全、审批责任和政策可信度风险最高的流程。

**Independent Test**: 使用一个普通员工账号和一组报销政策及附件，完成“选择材料—生成草稿—预览差异—批准—提交”全流程，并验证未批准、越权或越界文件操作均不会产生外部副作用。

**Acceptance Scenarios**:

1. **Given** 员工拥有指定材料的读取和编辑权限，**When** 员工要求助手整理报销材料，**Then** 系统只在该任务的隔离工作区中创建新草稿，并展示来源、变更和当前状态。
2. **Given** 草稿准备提交，**When** 员工尚未明确批准，**Then** 系统暂停操作并展示目标、文件、差异和可能副作用。
3. **Given** 员工确认提交且权限有效，**When** 系统执行提交，**Then** 系统只向已声明目标提交已批准版本，并留下可追溯结果。
4. **Given** 助手尝试访问未选择文件、正式政策原件或其他租户材料，**When** 操作被请求，**Then** 系统拒绝操作且不泄露文件内容。

---

### User Story 2 - 大规模并发下稳定使用 (Priority: P1)

企业员工在业务高峰期仍可稳定访问知识库、发起问答、保持流式进度连接并执行文件任务；系统过载时给出明确反馈，而不是长时间无响应、丢任务或重复提交。

**Why this priority**: 面向企业的能力必须由可复现数据证明，不能只依赖架构描述或单机演示。

**Independent Test**: 在记录清楚的环境中执行基线、负载、压力、突发、持续、长连接、文件工作流和租户隔离测试，保存原始数据，并核对容量、延迟、错误、资源增长和任务一致性。

**Acceptance Scenarios**:

1. **Given** 标准企业测试数据和目标运行环境，**When** 1,000 个会话同时使用系统，**Then** 系统达到成功标准中规定的响应、错误率和稳定性目标。
2. **Given** 1,000 条稳定流式连接，**When** 用户持续接收处理阶段和回答内容，**Then** 连接可被正确维持、断开、取消和清理，且不会持续占用已释放资源。
3. **Given** 请求量超过当前安全容量，**When** 新请求到达，**Then** 系统以可理解、可重试的方式限流或排队，不丢失任务、不重复执行副作用。
4. **Given** 两个租户同时参与负载测试，**When** 请求、缓存、任务和文件被并发访问，**Then** 任一租户均无法看到或影响另一租户的数据。

---

### User Story 3 - 使用统一可信的智能助手 (Priority: P1)

员工无论使用普通问答、流式问答、评估还是文件工作流，都获得一致的政策证据、处理阶段和权限行为；服务重启后，可恢复的任务不会悄悄丢失或重复执行。

**Why this priority**: 多套编排会造成结果、评估和审计不一致，也无法可靠支持长期任务与人工审批。

**Independent Test**: 对同一问题和证据分别触发普通问答、流式问答和评估，核对决策路径与证据门控一致；在文件任务等待批准时重启服务，验证任务恢复且不重复提交。

**Acceptance Scenarios**:

1. **Given** 相同用户问题、权限和知识库版本，**When** 通过不同入口执行，**Then** 系统采用同一决策规则并给出一致的证据结论。
2. **Given** 没有可靠政策证据，**When** 用户询问制度结论或要求生成材料，**Then** 系统明确说明证据不足，不使用记忆或无关内容代替依据。
3. **Given** 任务正在等待人工批准，**When** 服务重启后用户返回，**Then** 系统恢复到可核验状态，既不丢失审批上下文也不自行执行。
4. **Given** 工具或文件步骤失败，**When** 可重试条件满足，**Then** 系统只进行有限重试并向用户显示最终成功、失败或可恢复状态。

---

### User Story 4 - 在专业一致的界面中完成工作 (Priority: P2)

员工通过统一、清晰、可访问的桌面工作界面完成聊天、知识库、记忆、文件工作区和审批，不再面对粗糙、层级混乱或遮挡操作的页面。

**Why this priority**: 企业产品的可用性影响任务完成率、审批判断和用户信任，但必须建立在核心安全与稳定能力之上。

**Independent Test**: 让目标用户在常见窗口尺寸下独立完成问答、查证据、编辑文件、比较差异和批准提交，记录成功率、耗时、误操作和可用性反馈。

**Acceptance Scenarios**:

1. **Given** 用户首次打开应用，**When** 用户开始政策问答或文件任务，**Then** 主要操作、当前上下文和下一步清晰可见。
2. **Given** 文件草稿包含多处修改，**When** 用户进入审批，**Then** 用户可在一个连贯流程中查看文件树、预览、版本、差异、目标和审批状态。
3. **Given** 系统处于加载、空内容、离线、失败、恢复或无权限状态，**When** 用户查看相关页面，**Then** 页面提供明确状态、原因和可执行下一步。
4. **Given** 用户仅使用键盘或需要清晰焦点与高对比度，**When** 用户完成核心流程，**Then** 所有关键操作均可访问且状态可辨识。

---

### User Story 5 - 管理员治理企业能力 (Priority: P2)

企业管理员能够按租户和角色控制知识、文件、任务及提交权限，查看关键任务的审计记录和容量状况，并发现未完成、失败或跨存储不一致的资源。

**Why this priority**: 大规模企业部署需要权限治理、可观测性和恢复能力，避免把问题留给人工排查。

**Independent Test**: 配置两个租户与多种角色，验证授权矩阵、审计链、资源配额、任务恢复和数据清理结果均符合预期。

**Acceptance Scenarios**:

1. **Given** 管理员为角色配置最小权限，**When** 员工访问知识、文件或提交动作，**Then** 系统在服务端逐次校验租户和角色权限。
2. **Given** 一次问答或文件任务完成或失败，**When** 管理员按运行标识查询，**Then** 可追踪请求、证据、工具、审批、提交、重试和结果。
3. **Given** 文档被更新或物理删除，**When** 后台核对完成，**Then** 业务记录、检索内容和文件对象版本一致，异常项可被发现并恢复处理。

### Edge Cases

- 用户在审批前权限被撤销，系统必须在执行副作用前重新校验并拒绝提交。
- 用户关闭应用、网络中断或流式连接断开时，运行中的任务必须进入明确的取消、继续后台处理或可恢复状态。
- 同一提交被用户重复点击、客户端重试或服务恢复再次触发时，只能产生一次业务副作用。
- 文件名包含路径跳转、绝对路径、符号链接、快捷方式或异常编码时，不能逃离任务工作区。
- 上传内容为超大文件、嵌套压缩包、恶意文件或不支持格式时，必须在处理前拒绝或隔离并说明原因。
- 同一政策在任务期间产生新版本时，草稿必须保留其证据版本，提交前提示版本变化并要求重新核验。
- 检索服务不可用或只返回其他租户、旧版本、无关证据时，系统必须说明无法可靠回答，不能无证据继续生成正式结论。
- 审批者预览期间应用崩溃或会话过期时，任何未批准副作用都不能继续执行。
- 高负载时队列达到上限，系统必须明确拒绝或延后，而不是无限等待或耗尽资源。
- 多个用户同时编辑同一材料时，系统必须保留版本边界并阻止静默覆盖。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 让聊天、流式聊天、评估和文件工作流遵循同一套智能决策、证据门控、权限和审计规则。
- **FR-002**: 系统 MUST 为每次运行保存类型明确且可恢复的阶段状态，并使每个阶段具有清晰的输入、输出、失败、超时和有限重试结果。
- **FR-003**: 系统 MUST 限制单次智能体运行的工具调用次数与总时长，超过边界时进入可解释的失败或恢复状态。
- **FR-004**: 系统 MUST 将租户、用户和会话身份绑定到对话、消息、记忆、知识、文件、任务、审批、缓存和审计记录，并在每次访问时校验所有权。
- **FR-005**: 系统 MUST 根据企业角色授予最小权限，智能助手的权限不得超过发起用户当前拥有的权限。
- **FR-006**: 系统 MUST 为每个文件任务建立绑定租户、用户、会话和任务的隔离工作区，并仅允许访问用户为该任务明确选择或上传的文件。
- **FR-007**: 系统 MUST 保持正式政策原件只读，任何修改均创建带来源和版本关系的新草稿或新版本。
- **FR-008**: 系统 MUST 阻止通过路径跳转、链接、快捷方式、挂载点或异常文件名访问工作区之外的内容。
- **FR-009**: 系统 MUST 默认禁止文件任务访问任意网络、主机凭据和任意命令执行；确需执行的受支持处理必须受白名单和独立资源边界约束。
- **FR-010**: 系统 MUST 对上传文件执行格式、大小、总空间和恶意内容检查，并限制每项任务的处理时间和资源使用。
- **FR-011**: 系统 MUST 在覆盖、删除、发布、提交、上传、对外发送或导出之前暂停，向用户展示目标、文件、差异和副作用，并取得明确批准。
- **FR-012**: 系统 MUST 在执行已批准动作前再次校验权限和批准内容；未批准、已变更或已撤销授权的动作不得执行。
- **FR-013**: 系统 MUST 使所有写入和外部副作用可安全重试，并保证重复请求不会造成重复提交或静默覆盖。
- **FR-014**: 系统 MUST 为文件树、预览、版本、差异、审批、提交结果和失败恢复提供连贯的用户流程。
- **FR-015**: 系统 MUST 为聊天、知识库、记忆、文件工作区和审批提供统一的信息层级、视觉规则和交互状态。
- **FR-016**: 系统 MUST 为加载、空内容、错误、离线、恢复和无权限状态提供可理解的说明及下一步操作。
- **FR-017**: 系统 MUST 支持键盘完成核心工作流，并满足可见焦点、语义结构和可辨识对比度要求。
- **FR-018**: 系统 MUST 在常见窗口尺寸下保持核心操作可见、可用且无遮挡。
- **FR-019**: 系统 MUST 在多实例运行和服务重启条件下保持会话、任务、审批、限流和运行状态的一致性，不依赖单个进程的临时状态作为唯一记录。
- **FR-020**: 系统 MUST 将长时间解析、索引、文件和连接器工作作为可排队、可取消、可恢复且有明确终态的后台任务处理。
- **FR-021**: 系统 MUST 对模型调用设置租户和用户配额、并发上限、有限队列及明确的过载响应。
- **FR-022**: 系统 MUST 支持流式连接的心跳、断开检测、取消、超时、背压和资源清理。
- **FR-023**: 系统 MUST 以一个运行标识关联请求、流式连接、智能决策、检索、模型、工具、文件任务、审批、提交、重试和错误。
- **FR-024**: 系统 MUST 提供容量、延迟、错误、活跃连接、任务队列、外部模型使用、检索健康、文件结果和租户资源使用的可观测信息。
- **FR-025**: 系统 MUST 提供可重复的基线、负载、压力、突发、持续、长连接、文件工作流和租户隔离测试，并保存原始结果及测试环境信息。
- **FR-026**: 系统 MUST 将确定性替代模型的系统容量结果与真实模型服务的延迟和限流结果分开呈现，不得混合为同一容量结论。
- **FR-027**: 系统 MUST 保证企业业务记录、检索内容和原始或生成文件各自具有权威来源、版本关系和租户边界。
- **FR-028**: 系统 MUST 在文档更新和物理删除后核对业务记录、检索内容及文件对象，发现孤立、缺失或版本漂移时进入可恢复状态。
- **FR-029**: 系统 MUST 在检索不可用、证据无关或证据不足时明确拒绝给出制度结论；记忆不得覆盖当前政策证据。
- **FR-030**: 系统 MUST 让智能助手生成的文件在批准前保持草稿状态，不得自动进入正式知识库或业务提交目标。
- **FR-031**: 系统 MUST 在移除旧用户界面前验证新桌面工作界面已覆盖核心能力，并保留现有用户与知识库数据。
- **FR-032**: 系统 MUST 按“容量基线、无状态服务、统一智能编排、持久任务与配额、企业数据存储、文件沙箱与权限、桌面外壳、完整界面重设计、综合验收”的顺序分阶段迁移，每阶段均可独立运行和验证。
- **FR-033**: 系统 MUST 将本项目宪法作为规格、计划、实施、评审和发布的最高项目约束；冲突项必须记录为迁移债务或限期例外，不得静默忽略。
- **FR-034**: 系统 MUST 保持既有企业政策问答、证据引用、记忆边界、技能、工具、连接器和检索评估的诚实性约束，不得以框架名称夸大真实能力。

### Key Entities

- **租户**: 企业数据与资源的最高隔离边界，关联用户、角色、知识、任务、文件、配额和审计。
- **用户与角色授权**: 表示用户在租户内可读取、编辑、审批、提交或管理的范围及有效期。
- **智能运行**: 一次可追踪的问答、评估或文件任务，包含阶段状态、身份、证据、超时、重试和最终结果。
- **任务工作区**: 针对单次文件任务的隔离区域，包含明确授权的输入、生成草稿、资源限制和生命周期。
- **材料与材料版本**: 企业政策原件、用户附件或生成文件；记录来源、所有者、版本、校验信息、状态和对象位置。
- **文件变更集**: 草稿相对来源版本的可审阅差异，关联生成依据、文件清单和预期副作用。
- **审批请求**: 对高影响动作的人工授权，包含目标、文件、差异、权限快照、决定人、决定时间和状态。
- **提交任务**: 已批准副作用的唯一执行记录，包含幂等标识、目标、尝试次数、结果及恢复状态。
- **证据引用**: 当前运行使用的政策版本与内容位置，是制度结论和材料生成的权威依据。
- **容量测试运行**: 一次可复现测试的环境、负载模型、数据规模、原始指标、异常和结论。
- **审计事件**: 关联同一运行标识的访问、决策、工具、审批、提交、权限变化和错误记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在公布的标准环境和负载模型中，系统可同时支持至少 1,000 个活跃用户会话，服务端失败率低于 1%。
- **SC-002**: 在相同环境中，1,000 条流式连接可稳定维持；断开或取消后的连接资源在 30 秒内完成清理，且无持续增长趋势。
- **SC-003**: 不依赖外部内容生成等待时间的常规用户操作可持续达到每秒 200 次；其中 95% 在 500 毫秒内得到结果。
- **SC-004**: 95% 的流式任务在 1 秒内向用户显示首个处理阶段，内容生成耗时另行统计。
- **SC-005**: 30 分钟持续负载期间，吞吐和错误率保持在目标范围，内存、连接、任务或文件资源不存在持续无界增长。
- **SC-006**: 每次容量声明均附带可复现报告，完整记录版本、运行环境、硬件、数据量、负载、吞吐、p50/p95/p99、错误、断开、队列、资源和外部模型模式，并保留原始结果。
- **SC-007**: 所有未获批准、越权、跨租户和工作区逃逸测试均产生 0 次文件泄露、正式政策改写或外部提交。
- **SC-008**: 对重复点击、网络重试和服务恢复的测试中，每个已批准业务动作最多产生一次外部副作用。
- **SC-009**: 服务在等待审批或执行可恢复任务时重启，100% 的测试任务能够恢复为正确状态，且没有未经批准的自动继续或重复提交。
- **SC-010**: 目标员工在首次可用性测试中，至少 90% 能在 5 分钟内完成“选择材料—生成草稿—查看差异—批准或拒绝”的核心流程，且无引导员介入。
- **SC-011**: 至少 90% 的目标员工将核心界面的清晰度、一致性和操作信心评为 4/5 或更高。
- **SC-012**: 核心工作流在约定的常见窗口尺寸下通过全部键盘、焦点、语义和对比度验收，关键操作不存在遮挡或不可达情况。
- **SC-013**: 对相同问题、证据和权限，普通问答、流式问答与评估入口的证据门控结论一致率达到 100%。
- **SC-014**: 在无可靠证据、检索不可用或证据属于其他租户的测试中，制度性答案和正式材料提交的错误放行次数为 0。
- **SC-015**: 文档更新和物理删除后的自动核对能够发现 100% 的预置孤立、缺失和版本漂移故障，并使每项进入明确的已修复或待人工处理状态。
- **SC-016**: 新桌面体验替代旧界面前，现有核心用户流程和数据迁移验收通过率达到 100%，不存在未记录的数据丢失。

## Assumptions

- 首个企业容量基线采用项目宪法规定的 1,000 个并发会话、1,000 条流式连接和常规操作每秒 200 次；后续可依据真实企业容量计划提高，但不得在无测试证据时降低并宣称达标。
- 本次规格覆盖分阶段企业级重构，而不是一次性整体替换；每个迁移阶段必须保持可运行、可回退或可恢复。
- 首个文件业务纵向切片采用报销材料整理与提交，但沙箱、审批和权限模型应适用于其他企业材料工作流。
- 用户已经通过现有企业身份体系登录；具体登录协议不属于本功能范围，但所有授权必须在服务端执行。
- 正式政策发布、财务报销系统和企业连接器可在开发环境中使用明确标注的模拟目标；模拟结果不得被表述为真实生产集成。
- 外部内容生成服务的速度和限流与系统自身容量分开评估，以免网络供应商波动扭曲并发结论。
- 现有政策问答、检索评估、记忆管理和知识库数据必须在迁移中保留，其证据与诚实边界继续有效。
- 本次重构不包含移动端客户端；企业桌面端是唯一新的终端产品目标。
- 项目宪法 2.1.0 是本规格的最高治理依据；其中容量、统一编排、真实沙箱、存储职责、桌面端、安全、证据和增量迁移原则全部适用。

## Scope Boundaries

### In Scope

- 企业并发容量设计、过载行为、任务恢复、可观测性和可复现容量验证。
- 问答、流式问答、评估及文件任务的统一智能决策与持久状态。
- 租户隔离、角色权限、文件任务隔离、人工审批、版本、差异、提交和审计。
- 企业桌面端的信息架构、设计系统及聊天、知识、记忆、文件和审批核心体验重做。
- 权威业务记录、检索内容和文件对象的职责分离、版本一致性与物理删除核对。
- 在能力对等和数据迁移验收后移除旧终端界面。

### Out of Scope

- 由智能助手绕过用户批准自动报销、自动发布政策或自动向外部系统发送材料。
- 允许用户或智能助手执行任意脚本、任意网络访问或访问主机文件系统。
- 同时维护两套长期智能编排路径或两种桌面客户端架构。
- 将生成草稿在未批准前作为正式政策证据或自动写入正式知识库。
- 在本阶段交付面向公众的移动端应用。

## Dependencies

- 企业身份与角色信息必须可供服务端授权判断使用。
- 测试环境需提供可重复初始化的多租户业务数据、知识数据、文件和可控外部服务替身。
- 文件提交目标需定义可验证的测试接口或明确标注的模拟连接器。
- 发布容量结论需有固定或完整记录的测试环境，并保存原始测试产物。
- 数据迁移必须具备校验和恢复方案，旧界面移除依赖新桌面端能力对等验收。

## Governance & Migration Constraints

- **Applicable constitutional principles**: I–XII 全部适用，其中 I–IV、VI–VIII、XI–XII 为本重构的直接验收边界。
- **Contract impacts**: 用户问答与流式阶段、智能运行状态、文件任务与审批、权限、桌面能力边界、审计和评估输出的现有契约均可能变化，后续计划必须逐项列出兼容或迁移方式。
- **Migration risks**: 主要风险包括多实例状态丢失、双编排结果漂移、跨租户读取、工作区逃逸、未批准副作用、旧数据迁移丢失、检索与文件版本漂移，以及容量测试环境与生产差距。
- **Required validation**: 每个阶段必须执行适用的功能、集成、租户隔离、文件沙箱、恢复、数据核对、桌面端端到端和容量测试；任何未执行项目均需明确披露。
- **Exceptions**: 任何偏离宪法的例外必须记录范围、理由、风险、责任人、补偿措施与到期日，且不得作为永久默认。
